# Conformance cases

Test cases every implementation of the light rules (`docs/board/light-v1.md`), of the command protocol (`docs/protocol/protocol-v1.md`) and of the WiFi and update rules (`docs/board/wifi-and-updates-v1.md`) must pass. The native tests run the light cases against the light engine, the protocol cases against the protocol core, and the rest against the pure libraries (`test/test_conformance`).

Expected values are worked out by hand from the specification, with a calculator for the formulas. They are never generated by running the engine, the firmware or the simulator.

## Light

- `light/curve.json`: lightness to duty.
- `light/power.json`: the power limit on given duties, in channel order red, green, blue, white.
- `light/record.json`: the stored record of the light settings, encoded and decoded.
- `light/sequences/*.json`: a start, events and expected outputs:
  - `settings`: the stored light settings at the start, as in the protocol (missing ones take their defaults).
  - `seed`: the seed of `twinkle`, 1 when missing.
  - `limit_mw`: a power limit other than the firmware's.
  - `events`: in time order, each with `at` (milliseconds since the start) and either `set` (settings changed as by `settings_set`) or `light` (`true` or `false`).
  - `expect`: each with `at`, `duties` (red, green, blue, white) and optionally `on`, `power_scale` and `timer_remaining_s`.

The light starts at time 0. The runner ticks every 10 ms, and also at an expected time off that grid. Events at a time apply before the output at that time is computed; an event between two ticks applies at the next tick.

## Protocol

`protocol/*.json` are exchanges of lines and replies, run against the protocol core (`protocol::handle_line`) with a virtual clock and the light engine, each case starting from a fresh board: default settings, light starting at time 0, `boot_id` 4242, nothing remembered. Each case has a `description`, an optional `transport` (`usb`, the default, or `wifi`) and `steps`, run in order. A step is one of:

- `send` and `expect`: a line goes to the board and exactly one reply line must come back, or none when `expect` is `null`. Over USB the line and its newline go through the line reader, as the serial port delivers them (so one carriage return before the newline is dropped, a line over the limit is `bad_frame` or ignored, and a newline inside a line makes two lines); over `wifi` the line is one WebSocket message, as it is, so a `\r` at its end stays in the JSON.
  - `send` is a string, sent as the line it is, or an object, which the runner serializes and frames with the right checksum.
  - `send_hex` (hexadecimal bytes) replaces `send` for bytes a JSON string cannot hold, such as invalid UTF-8 or a raw NUL.
  - `send_padded` (`prefix`, `fill`, `count`) builds a long line: the prefix followed by `count` copies of one character.
  - `transport` overrides the case's transport for this step.
  - `note` is for readers; the runner ignores it.
- `advance_ms`: the virtual clock moves by exactly this many milliseconds, and the light ticks at each multiple of 10 ms it crosses, at that time. Steps of any size add up: two steps of 5 ms tick at 10 ms, and a step of 11 ms from 9,989 ticks at 9,990 and 10,000. The simulator's `!advance` follows the same rule.
- `event`: `wifi_open` or `wifi_close` (a WiFi connection opened or closed), `storage_fail` or `storage_ok` (writes to the settings memory fail, or work again), `storage_read_fail` or `storage_read_ok` (reads of the settings memory fail with an I/O error, or work again; they take effect at the next `!restart`, when the records are read).
- `control`: a control line of the simulator, run at the current time (see below).
- `close_requested`: `true` or `false`, a step of its own: whether a request made without a line (a WiFi client that stayed unauthenticated for 10,000 ms) asked to close the WiFi client's connection.
- `close` on a `send` step: whether that request asked to close the WiFi client's connection (a failed login, a new token, network login turned on, a reset). Without it the runner ignores the request.

The runner starts every case with the firmware version `0.1.0`, hostname `zenit-0000`, no network, no update source and the light fading in from time 0. Cases that read the light start with `advance_ms` 1,100 so the fade is over.

The control lines are the simulator's own (`--protocol`; `src/sim_control.cpp`), so the same words drive a case and a hand run:

- `!net state=... ssid=... rssi=... ip=... synced=0|1 epoch=...`: sets what the network reports (`epoch` is Unix seconds at the time of the line; the clock then runs with virtual time). The state follows the stored network only when the stored network changes.
- `!store-wifi ssid=NAME password=TEXT`: stores a network as a finished Improv setup does. `!token TEXT` sets the token; `!random HEX` queues the bytes the next random draws return (a login nonce, a token), so values that depend on randomness are known by hand; `!version X.Y.Z` sets the running version.
- `!update manifest TEXT` serves that text as the update manifest, `!update fail unreachable|not_published|tls_error` makes the check fail, `!update firmware SIZE FILL` serves a file of SIZE bytes of the byte FILL (its SHA-256 is printed as `!sha256 HEX`), `!update download ok|unreachable|tls_error|bad` scripts the download. With `web` after `!update` the same lines script the web app's source (`!update web image VERSION MIN MAX` serves a web image of one page, `!update web publish VERSION MIN MAX` serves it with a manifest that describes it). `!www load VERSION MIN MAX` puts such an image in the `www` partition, `!www erase` leaves none and `!www fail begin|write|end|none` fails the next web install there, and `!www fail busy` fails its start as a page still being sent that it could not wait for. The simulator starts with a web image of version 1.0.0 that speaks protocol 1, and its source offers that same image.
- `!firmware fail begin|write|end|activate|mark_valid|none` injects a failure in the slot steps, `!firmware trial 0|1` and `!firmware invalid 0|1` set the slot state.
- `!restart` restarts the board (into the installed image on trial when an install activated one), `!restart as X.Y.Z` restarts into that image when it reports another version than its manifest said, `!restart rollback` restarts as the bootloader does after a failed trial, `!restart lost` as after a power cut before the switch.
- `!scan NAME:RSSI:YES|NO ...` sets the networks a scan finds.

A reply must be a frame with a correct checksum, strict JSON, and no newline inside. `expect` is compared field by field: the same fields, no more and no fewer, the same values, numbers by value. An object `{"$any": "string"}` (or `"integer"`, `"boolean"`) matches any value of that type, for what varies with the build (`info.firmware`). It also stands for a value a case does not test and that depends on timing the case does not pin: `status.update.web.last_result` in the cases about the firmware's updates (the web side has its own cases, `command_update_web.json` and `command_update_web_check.json`, with exact values), `last_check`, and the jittered `retry_in`. An error reply must carry a `message`, which `expect` leaves out since it is for people.

A text matched by `{"$pattern": "regular expression"}` is any string that matches it (a token: `^[a-z0-9]{16}$`).

The checksums of the raw lines were computed with Python's `zlib.crc32`, an implementation independent of the firmware. The expected values were typed by hand from the specifications.

## Clients

`client/replies.json` holds replies a client must accept or refuse, by command: `command`, `valid`, a `note` for readers and `reply`, the reply body without `seq`. The web app runs it through `validBody` (`web/test/replies.test.ts`) and the command line client through `valid_body` (`tools/test_zenit.py`), each reading the file's numbers as written (`60.0` is a fraction, an integer field refuses it). Every command of the clients' reply tables has a valid and an invalid case. Both clients also read the board's replies of `protocol/*.json`.

## WiFi, updates and Improv

Cases for the pure logic of milestone 4, each file with a `description`:

- `net/hash.json`: SHA-256 and HMAC-SHA256 digests (computed with an independent implementation).
- `net/origin.json`: the WebSocket origin check and the origin of a site address. `net/ws_message.json`: reassembly of WebSocket frames into one line, with the close statuses. `net/http.json`: what a request path means for the served app, and the answer headers.
- `net/scan.json`: the list of a WiFi scan (one entry per name, strongest access point, best 16 names, sorted).
- `net/wifi.json`: the wait between tries, the state a disconnect reason leaves, the power fallback, the hostname and the checks of the network name and password.
- `board/stored.json`: what the board reads at start: the blob that holds both records, a damaged blob, nothing stored.
- `board/record.json`: the 255-byte board record, both ways (`record_hex`), laid out by an independent script from the table of the specification.
- `update/web_image.json`: the web image of the `www` partition, header fields and body bytes laid out by hand from the specification, valid and refused, read by the board's reader (native tests) and by `tools/web_image.py`.
- `update/semver.json`, `update/manifest.json`, `update/web_manifest.json`, `update/schedule.json`, `update/boot.json`: versions and precedence, the firmware and web manifests (valid and refused texts), the install window and the check schedule, and what the boot does with the update record.
- `improv/frames.json`: the packets the board writes, the RPC arguments, and byte streams that mix Improv frames with protocol lines (`pass_hex` is what goes on to the line reader).

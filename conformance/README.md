# Conformance cases

Test cases every implementation of the light rules (`docs/board/light-v1.md`) and of the command protocol (`docs/protocol/protocol-v1.md`) must pass. The native tests run the light cases against the light engine and the protocol cases against the protocol core (`test/test_conformance`).

Expected values are worked out by hand from the specification, with a calculator for the formulas. They are never generated by running the engine, the firmware or the simulator.

## Light

- `light/curve.json`: lightness to duty.
- `light/power.json`: the power limit on given duties, in channel order red, green, blue, white.
- `light/record.json`: the stored record of the light settings, encoded and decoded.
- `light/sequences/*.json`: a start, events and expected outputs:
  - `settings`: the stored light settings at the start, as in the protocol (missing ones take their defaults).
  - `seed`: the seed of `twinkle`, 1 when missing.
  - `limit_mw`: a power limit other than the firmware's.
  - `events`: in time order, each with `at` (milliseconds since the start) and either `set` (settings changed as by `settings_set`) or `light` (`true` or `false`).
  - `expect`: each with `at`, `duties` (red, green, blue, white) and optionally `on`, `power_scale` and `timer_remaining_s`.

The light starts at time 0. The runner ticks every 10 ms, and also at an expected time off that grid. Events at a time apply before the output at that time is computed; an event between two ticks applies at the next tick.

## Protocol

`protocol/*.json` are exchanges of lines and replies, run against the protocol core (`protocol::handle_line`) with a virtual clock and the light engine, each case starting from a fresh board: default settings, light starting at time 0, `boot_id` 4242, nothing remembered. Each case has a `description`, an optional `transport` (`usb`, the default, or `wifi`) and `steps`, run in order. A step is one of:

- `send` and `expect`: a line goes to the board and exactly one reply line must come back, or none when `expect` is `null`. Over USB the line and its newline go through the line reader, as the serial port delivers them (so one carriage return before the newline is dropped, a line over the limit is `bad_frame` or ignored, and a newline inside a line makes two lines); over `wifi` the line is one WebSocket message, as it is, so a `\r` at its end stays in the JSON.
  - `send` is a string, sent as the line it is, or an object, which the runner serializes and frames with the right checksum.
  - `send_hex` (hexadecimal bytes) replaces `send` for bytes a JSON string cannot hold, such as invalid UTF-8 or a raw NUL.
  - `send_padded` (`prefix`, `fill`, `count`) builds a long line: the prefix followed by `count` copies of one character.
  - `transport` overrides the case's transport for this step.
  - `note` is for readers; the runner ignores it.
- `advance_ms`: the virtual clock runs this many milliseconds, ticking the light every 10 ms.
- `event`: `wifi_open` or `wifi_close` (a WiFi connection opened or closed), `storage_fail` or `storage_ok` (writes to the settings memory fail, or work again).

A reply must be a frame with a correct checksum, strict JSON, and no newline inside. `expect` is compared field by field: the same fields, no more and no fewer, the same values, numbers by value. An object `{"$any": "string"}` (or `"integer"`, `"boolean"`) matches any value of that type, for what varies with the build (`info.firmware`). An error reply must carry a `message`, which `expect` leaves out since it is for people.

The checksums of the raw lines were computed with Python's `zlib.crc32`, an implementation independent of the firmware. The expected values were typed by hand from the specifications.
